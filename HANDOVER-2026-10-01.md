## 2. Window scaling: measured behaviour on this machine

Scale arithmetic for this session: `Xft.dpi = 232` → `232 / 96 = 2.4167×`. That equals mutter scale 1.25 ×
`text-scaling-factor` 1.21 ÷ 0.625 XWayland oversampling — so deriving the factor from Mutter's bare 1.25 would render
far too small, and was tried and rejected.

| Setting | Exit and restart mid-session | Reboot (login autostart) |
|---|---|---|
| Automatic, build `207448c` (pin-only) | ~241.7% — correct | **tiny window** — race lost |
| Pinned 240%, any build with the card | correct | **correct — survives reboot** |
| Automatic, deployed `2fd57b5` (waits for hint) | correct | **not yet tested; next reboot decides** |

Mechanism: the app is an X11 client through XWayland and takes its size from the session's `Xft.dpi` resource. Login
autostart routinely reads it before GNOME writes it, so Avalonia initialises at 1.0 and the window opens at a fraction
of its intended size; launching manually later in the same session looks fine. That timing dependence is exactly why
this looked intermittent for so long, and why "it was fine when I tested it" kept being both true and useless.

The deployed fix makes **Automatic wait** — polling `xrdb -query` every 200 ms for up to 3 s before Avalonia reads the
display — then lets the toolkit scale itself unaided. It is keyed on `DISPLAY`, not `WAYLAND_DISPLAY`, because the
systemd autostart unit may not carry the latter and would otherwise skip the wait entirely.

**Pinning stays the guaranteed path**, and does not depend on hint timing at all. Avalonia ignores a wildcard
(`*=2.4` is a silent no-op) and requires real connector names, so `DisplayConnectors.Detect()` emits
`DP-2=2.4;DP-3=2.4`; detection uses Mutter's `GetCurrentState` over gdbus with an `xrandr --listmonitors` fallback.

Cosmetic defect: the Settings note reports "suggests 242%" (241.67% rounded to a whole number) while the nearest
selectable step is 240%, so it advertises a value that cannot be chosen. Should round to an available step or be
labelled "session default".

## 3. The invisible-window incident

**Symptom on the real GNOME Wayland session:** window mapped at the correct size with **nothing painted**, floating
above other windows and swallowing clicks. Desktop icons and every other application rendered normally, which ruled out
a compositor-wide failure early.

**Ruled out:** leftover compositor damage from my repeated launches and kills. The user rebooted, after which `ba2aa30`
rendered correctly in that same session — so the fault is in code built after `ba2aa30`.

**Prime suspect, still unproven:** commit `2805d84`'s automatic rescue path setting `AVALONIA_SCREEN_SCALE_FACTORS`. It
is the only change in that day's work that alters how the toolkit sizes and presents its surface. The deployed build
never sets that variable except from an explicit user pin, and pins are known good on this machine — which is
consistent with the override being the problem but does not prove it, because the suspect builds also carried other
edits.

**Why it was not caught here:** every Release build was "verified" by measuring window geometry with `xwininfo`. A
fully transparent window measures identically to a working one, so those checks could not have detected it at any
point. Compounding that, all my pixel verification happened on Xvfb, which has no GLX and therefore always renders in
software — the one environment incapable of showing this bug. See §5.

## 4. On `main`, deliberately NOT deployed

Held back because it landed the same day as the regression and was never verified with real pixels:

- NVMe drive-model naming in overlay and sensor menus (`WD_BLACK SN850X · aa:00.0`), bus id first because menus
  truncate from the right.
- `MenuText()` escaping of `_` in MenuItem headers — Avalonia consumes a single underscore as an access key, which had
  produced labels like `PCHCHIPCPU_MAX_TEMP`.
- Tray click-to-open (`tray.Clicked`) and `RestoreMainWindow()`, which also undoes a minimize. Previously the tray icon
  had no click handler at all and `Open` used `Show()+Activate()`, so once the window was hidden there was no way back.
- `StartMinimized` actually implemented: Avalonia auto-shows `lifetime.MainWindow`, so starting minimized requires
  leaving it unassigned plus `ShutdownMode.OnExplicitShutdown`. Setting `WindowState.Minimized` beforehand does not stick.
- `OPENFAN_RENDER=software|retained` escape hatch (`X11PlatformOptions.RenderingMode`, `UseRetainedFramebuffer`). Note
  these types are in namespace `Avalonia`, not `Avalonia.X11`.
- Test suite: **197 passing**.

Re-land these **one at a time**, each verified by pixel capture before it reaches `~/my_programs/openfan-linux`. The
batch is what made this incident impossible to bisect.

## 5. Verification standard (non-negotiable)

1. **Geometry proves nothing.** Verify by capturing pixels and looking at them — never by window size, map state, or a
   process being alive.
2. **Xvfb cannot expose presentation bugs.** No GLX there means Avalonia always renders in software; lab screenshots
   prove startup, layout and label text only.
3. **Never launch-and-kill repeatedly on the user's live desktop.** Use `hd` on `:99`. Touch `:0` at most once at a
   time, only with the user's agreement, and let them initiate it.
4. Capture on the lab display with `hd shot`. On the real session `import -window root`, `xwd` and `gnome-screenshot`
   all failed, and `import -window <id>` returns black for GL-backed windows — do not trust that result either way.
5. `strings` needs `-el` to read .NET metadata (UTF-16); without it, labels present in an assembly appear absent. A
   single-file self-extracting bundle hides its managed assemblies from `strings` entirely.

## 6. Operational traps (each already cost time)

- `pkill -f <pattern>` **kills the shell running it** when the pattern text appears anywhere in that same command line.
  Use a bracketed pattern (`openfan[.]dll`) and keep the literal out of the line, or kill recorded PIDs.
- `kill $!` after `setsid … &` kills the wrapper, not the app (PID off by one). Verify the real PID, and check the log
  for `OpenFan is already running (lock: /run/user/1000/openfan.lock)` — a stale instance silently makes a test measure
  the old build.
- `dotnet test tests/OpenFan.Core.Tests` does **not** rebuild the Avalonia app; build `src/OpenFan.Linux.App` first.
- Solution is at repo root (`OpenFan.Linux.sln`). Filesystem is fuseblk, so exec bits are unrepresentable and
  `git config core.fileMode false` is set.
- Live config path comes from `~/.config/openfan/active` → `/home/russellm/Documents/openfan2.json`. Never edit it while
  an instance runs — the app saves over it. Error log: `~/.local/share/openfan/errors.log`.
- Reinstall `/usr/local/lib/openfan/openfan-helper` after any change to `OpenFan.Core` or `OpenFan.Linux.Hw`, then
  `systemctl restart openfan-helper`.
- Root only via `~/.dsh/skills/grant-root/scripts/root-run.sh`. Approval prompts are disabled in this session — never
  set `sandbox_permissions`.
- `/tmp` is reaped mid-session; keep worktrees and build outputs under `/mnt/8TB`.

## Implemented behavior

### CPU frequency controls

The 9970X has 32 physical cores and 64 SMT threads. The UI intentionally groups siblings into
32 core rows, using kernel socket/core topology. Frequencies are kernel-reported samples, not
effective clocks. The table supports an all-core cap or **Set individual cores**, which enables
per-row MHz fields populated from live caps and disables the all-core controls. Applying a core
cap covers its sibling policies. Pending edits survive live refreshes; batch validation/readback
and rollback protect against partial application.

**CPU frequency reboot persistence is still a plan, not implemented or enabled.** See
[persistence plan](docs/cpu-frequency-persistence-plan.md). The existing CPU socket PPT power
limit has its own persistence feature; do not confuse that with frequency-cap persistence.

### Sensors, editing and saved visibility

Compact Current / Min / Max / Average / Unit tables share background samples. libsensors is
the default hwmon reader; a visible sysfs temperature/fan fallback handles library/config errors.
NVIDIA telemetry comes from NVML, including real RPM for all five GPU fans. ECC counters use EDAC.

Names use a temporary edit box. Painting and automatic inventory refresh defer during editing;
sampling and fan control continue. Hidden categories and collapsed groups/devices save immediately
in the profile and stop unneeded reads. Status flags are optional. Required active curve, overlay
and visible-page inputs remain live even if their sensor table is hidden. One in-flight read may
finish. Settings replacement uses a same-directory rename. Restart persistence was tested in the GUI.

Inventory discovery still runs on the UI thread every five seconds or on Refresh. Other page readers
and device latency can still cause stalls; this is not a complete background ownership redesign.

### DDR5 memory temperatures

Four SPD5118 hubs are read through existing libsensors/hwmon after the user's working binding setup.
Controllers `AMDI0010:01` and `AMDI0010:02` each expose addresses `0x50` and `0x52`. Stable identities
use controller/address rather than boot-specific hwmon or adapter numbers. No physical DIMM slot
letters were guessed. Memory temperatures are usable in curves and overlay tiles.

Each row includes read-only configured limits: Low 0 °C, High 55 °C, Critical low 0 °C and Critical
high 85 °C at verification. Limits are separate from measured Min/Max and temperature pickers.
The integration did not change hardware thresholds. The existing binding survived the morning boot;
no new reboot was performed during application integration.

`packaging/dram-temps/`; see [DRAM notes](DRAM-TEMPS-README.md). Do not repeat the unsuccessful

### NVMe temperatures, activity and SMART health

Five controllers are present:

| Controller | PCI address | Model | Firmware |
| --- | --- | --- | --- |
| nvme0 | 0000:c2:00.0 | SOLIDIGM SSDPFKNU020TZ (P41 Plus 2 TB) | 001C |
| nvme1 | 0000:c1:00.0 | Samsung SSD 970 EVO Plus 2 TB | 2B2QEXM7 |
| nvme2 | 0000:a9:00.0 | WD_BLACK SN850X 8 TB | 638211WD |
| nvme3 | 0000:ad:00.0 | WD_BLACK SN850X 8 TB | 638201WD |
| nvme4 | 0000:aa:00.0 | WD_BLACK SN850X 4 TB | 624331WD |

- Composite is **Drive temperature (composite)**. Numbered probes are **Internal temperature N (unmapped)**. Exact manufacturer controller/NAND mappings were not established; do not infer locations from ordinal or temperature. Native custom labels and aliases take precedence. Existing temperature ids remain compatible.
- Valid composite high/critical limits appear inline. Bogus internal 65,261.85 °C placeholders and Kelvin-zero minima are excluded. Headings/source menus identify model and PCI address.
- **Drive activity (NVMe)** adds seven metrics per drive: read/write decimal MB/s, read/write/total activity, and read/write decimal GB totals since boot/device-counter reset. Reads whole namespace block statistics without counting partitions twice. Pause/resume, resets, missing data and namespace changes reset rate baselines. Linux read/write request-time activity can exceed 100%; total busy-time activity is capped at 100%. These are not identical to Windows performance counters.
- **Drive health (NVMe)** adds 20 SMART fields per drive: endurance/spare, lifetime decimal TB, command/power/error counters, thermal history and current warnings. Each drive shows a decoded warning summary and update/error status. Failures become unavailable, not perfect zeros. Large counts use abbreviations with full current values on hover. Floating-point display may round integer counts beyond 2^53.
- SMART runs in an independent 30-second background batch and uses its own transient helper connection. It cannot hold the GPU fan client's socket lock or delay the regular fan sample. Both new groups support saved hide/collapse and paused polling.
- Fixed helper command `nvmesmart <nvmeN> <identity-hash>` checks local PCI/model/serial identity and allows only a bounded, read-only 512-byte SMART Get Log operation on the validated controller. No caller-selected paths, opcodes, namespace selections or drive writes. Existing helper installations need the new helper for SMART. No nvme-cli/smartctl package or subprocess polling is required.
- Production uses RAE=0, matching the kernel. Samsung rejected an initial diagnostic RAE=1 request; that may contribute an unsupported-command error-log entry. Error-log counts are not synonymous with media failures. All five drives reported zero media errors during verification.
- Transient sessions are pruned and never own GPU fans. A helper shutdown race discovered in testing was fixed by joining the accept loop before snapshotting/draining sessions; a 25-iteration regression checks fan restoration before shutdown returns.

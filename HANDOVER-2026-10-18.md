## CPU frequency feature — previous revision (21:22 PDT)

The app now includes a live core-clock table and frequency ceilings, implemented and deployed in this workspace. The preparation audit below describes the earlier baseline.

- New files: `src/OpenFan.Linux.Hw/CpuFrequencyMonitor.cs`, `src/OpenFan.Linux.Hw/CpuFrequencyControl.cs`, `src/OpenFan.Linux.App/CpuFrequencyPage.cs`, and `tests/OpenFan.Core.Tests/CpuFrequencyTests.cs`.
- The user requested **32 physical-core rows**, grouping both SMT threads per row, rather than 64 separate thread rows. Current is the maximum available sibling reading; minimum/maximum/average are per-core sampled-clock statistics. Topology comes from kernel socket/core ids, never CPU-number arithmetic. Current clocks are kernel-reported samples, not effective clocks.
- The table refreshes once per second on a background task while the CPU page is visible. It has two columns of 16 rows at normal width and stacks at narrower widths. Hover exposes sibling ids, individual readings and sources. Reset statistics starts a new sampling window.
- All cores is the default cap target. Selecting/clicking a core targets both sibling policies. Other machines' shared policy memberships are respected and affected CPUs are displayed.
- The helper accepts `cpufreq <comma-separated-policy-ids>|all <kHz>|default`. It validates every policy before writes, serializes requests, waits up to 500 ms for asynchronous policy readback, and attempts verified rollback on failure. An immediate-readback implementation failed on real hardware because the kernel had not yet published the new ceiling; the bounded wait fixes this and has a regression test.
- Frequency caps are deliberately **live only**. They are not saved or re-applied on startup, and remain until reboot or another power manager changes them. Hardware maximum uses current `cpuinfo_max_freq`; it does not change boost, EPP, governors, minimum frequency, PPT or BIOS settings.
- Machine: amd-pstate-epp, 64 policies, 32 cores/64 threads, per-policy boost off, current allowed range 1,223.141–4,000 MHz. Existing cpupower and turbostat were sufficient; no packages installed.
- Verification: 223 tests pass (197 original + 26 new cases); app/helper Release publishes succeed with existing warnings. Real-machine tests verified a 3,000 MHz cap on every policy, 2,800 MHz on core 0's policies 0/32 only, invalid-cap rejection, and complete restoration. Turbostat measured approximately 3,013 MHz under load for a 3,000 MHz request; delivered clocks can differ slightly from the policy ceiling, noted in the UI/docs.
- Headless UI tested against the real machine's read-only telemetry and a private root-helper socket, using isolated config/runtime directories with fan application off. UI Apply cap set all policies to 3,200 MHz; Hardware maximum restored all original settings. Both wide/narrow layouts and final pixels were inspected. This is a software-rendered Xvfb layout check, not a live GNOME rendering assertion.
